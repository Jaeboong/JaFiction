## 1. 배경 — 현재 모델과 무엇을 바꾸는가

자소전의 현 데이터 모델은 **"백엔드 서버는 사용자 콘텐츠를 0 저장"** 이다.
- 서버 DB(Postgres): 인증·세션·기기 등록·페어링 메타데이터만 (`users`/`sessions`/`devices`/`device_users`).
- 러너 로컬(사용자 머신): 프로젝트·문서·실행기록·자소서·API키 전부 파일로 저장.
- 웹은 백엔드를 **중계기**로만 쓴다 — `POST /api/rpc` → 백엔드가 연결된 러너를 찾아 포워딩 → 러너가 로컬 읽어 응답. 상태는 러너가 `state_snapshot`(SidebarState)을 Redis 통해 웹으로 push.

본 기능은 이 **프라이버시 경계를 의도적으로 연다**: 사용자 경험 데이터를 서버에 올려 다기기 간 일관된 뷰를 만든다. 따라서 프라이버시 설계(§5)가 선택이 아니라 필수다.

## 2. 확정된 요구사항 (사용자 Q&A, 2026-05-27)

| 항목 | 결정 | 비고 |
|------|------|------|
| **목적** | **다기기 일관성** | 노트북·데스크탑 등에서 웹 접속 시 같은 경험 데이터를 본다. 백업/서버측 실행이 목적이 아님 |
| **전제** | 러너는 항상 켜져 있음 | 서버측 에이전트 실행 없음. 러너가 계속 컴퓨트 엔진. 이 기능은 **데이터 미러링/일관성** 문제 |
| **트리거** | **수동 1회** (설정 탭 버튼) | 지속 백그라운드 동기화 아님 → 동기화 엔진/변경 감지 불필요 |
| **충돌 처리** | **합산(union) + 중복 제거** | 파괴적 last-write-wins 아님. 로컬∪서버 후 dedup |
| **v1 범위** | **내 경험(프로필 문서) + 지원서(프로젝트 컨텍스트 문서·메타)** | **실행 기록(runs)·트랜스크립트 제외** |
| 진행 방식 | 단계적 (v1 → v2) | 동기화·암호화·옵트인을 v1에서 검증 후 확장 |

## 3. 제안 아키텍처 — 로컬 우선 + 수동 양방향 union 동기화

advisor 검토 반영: **러너 저장소를 서버로 바꾸는 안(매 읽기 네트워크 왕복)은 런 지연·취약성으로 폐기.** 또한 웹의 데이터 경로(웹←러너 snapshot)는 **그대로 둔다.**

동작:
1. 설정 탭에서 사용자가 **"서버에 동기화"** 버튼을 누른다(옵트인 토글 ON 상태에서).
2. 러너가 **양방향 union 동기화**를 1회 수행:
   - **Pull**: 서버의 사용자 콘텐츠를 가져와 로컬에 **병합(union)**, 중복 제거.
   - **Push**: 로컬의 콘텐츠를 서버로 **병합(union)** 업로드.
   - 결과: 동기화 직후 `로컬 == 서버 == union(로컬, 서버)`.
3. 웹은 평소대로 러너 `state_snapshot`을 읽는다. 동기화로 로컬이 이미 통합셋이 되었으므로 **웹은 자동으로 통합된 데이터를 본다.**

> "서버 동기화 활성 시 서버만, 아니면 로컬만 보여준다"는 초기 구상은 **union 의미론에서 자연 수렴**한다(동기화 후 둘이 동일). 그래서 별도의 웹 데이터 경로 전환이 필요 없다. 다기기 일관성은 "각 기기가 동기화를 누르면 서버의 union을 받아간다"로 달성된다.

### 3.1 중복 제거(dedup) 키
- 문서 식별: **콘텐츠 `sha256`** 기준(업로드 청크 경로에 이미 sha256 존재) + 제목/스코프 보조.
- 동일 콘텐츠가 두 기기에 있으면 **1개로** 수렴.
- 프로젝트: `slug` 기준 병합(같은 slug면 한 레코드, 필드 차이는 §6 오픈 질문).

## 4. 백엔드 저장 (신규)

현재 콘텐츠 테이블 없음. 휴면 `projects_meta`/`runs_meta`는 미사용 placeholder. v1에서 신규 콘텐츠 저장 도입:
- 테이블(안): `synced_profile_documents`, `synced_project_documents`, `synced_projects` — 모두 `user_id` FK, dedup 위한 `content_sha256`, `scope`, `title`, 메타.
- **문서 원본 blob**: PDF·PPTX 등 바이너리. 저장소 선택은 오픈 질문(§6) — Postgres `bytea` vs 오브젝트 스토리지.
- **암호화 at rest 필수**(§5).
- 신규 RPC/HTTP: `sync_push`(러너→서버 업로드), `sync_pull`(서버→러너), 또는 단일 `sync_run`(양방향 union). op 추가 시 `OP_NAMES`/`RpcRequestSchema` 동기화.

## 5. 프라이버시 — 필수 (협상 불가)

이 기능은 프라이버시 모델을 의도적으로 깬다. 다음을 v1 필수 요건으로 못박는다:
1. **서버 암호화 저장**(at rest) — "검토"가 아니라 의무.
2. **명시적 옵트인** — 토글 켤 때 **"무엇이 기기를 떠나 서버로 가는가"**(프로필 문서 내용, 지원서 컨텍스트 문서 내용, 회사명·채용정보 등 프로젝트 메타)를 설명하는 모달.
3. **연동 해제 시 서버 데이터 삭제 경로** — 토글 OFF → 서버측 사용자 콘텐츠 wipe.
4. **로그 규율** — 백엔드 로그에 문서 내용·민감 필드 절대 금지.
5. v1은 실행 트랜스크립트를 올리지 않으므로(범위 제외) 가장 민감한 LLM 대화·드래프트는 서버에 남지 않는다.

## 6. 한계 / 오픈 질문 (구현 플랜 전 확정 필요)

1. **삭제 전파**: pure union은 삭제를 전파하지 않는다(기기 A에서 지운 문서가 서버에 남아 다음 동기화 때 부활). v1은 이를 수용? 아니면 tombstone(삭제 마커)을 v1에 넣을지. → **권장: v1 수용(누적), tombstone은 v2.**
2. **프로젝트 필드 충돌**: 같은 `slug`의 프로젝트가 두 기기에서 서로 다른 필드(회사명·rubric 등)를 가질 때 union이 모호. 문서는 sha256로 깔끔하지만 **구조화 레코드는 병합 규칙 필요**. → 오픈 질문: 최신 `updatedAt` 우선? 필드별 병합?
3. **blob 저장소**: Postgres `bytea`(단순, 단일 DB) vs 오브젝트 스토리지(대용량 적합, 인프라 추가). 사용자 문서 크기 분포에 따라.
4. **동기화 단위**: 단일 "서버에 동기화" 버튼 1개(전체 union) vs 소스별(내 경험만 / 지원서만) 선택.
5. **다기기 동시 편집**: 두 러너가 동시에 같은 항목을 바꾸는 진짜 동시성은 v1 범위 밖(단일 활성 러너 가정 유지). 누적 union이라 파괴는 없음.
6. **실행 기록(runs)**: v2로 명시 연기 (대용량 트랜스크립트 + 가장 민감).

## 7. 단계 제안

### v1 — 수동 union 동기화 (내 경험 + 지원서 컨텍스트)
- 설정 탭: "서버 연동" 옵트인 토글 + 설명 모달 + "지금 동기화" 버튼 + "연동 해제(서버 데이터 삭제)".
- 백엔드: 콘텐츠 테이블 3종 + blob 저장 + 암호화 + `sync_*` 엔드포인트.
- 러너: 양방향 union 동기화기(pull→merge→push), sha256 dedup.
- 범위: 프로필 문서 + 프로젝트 컨텍스트 문서 + 프로젝트 메타. **runs 제외.**
- 테스트: union/dedup 단위 테스트, 암호화 왕복, 시크릿/콘텐츠 로그 누출 회귀, 옵트인 OFF 시 서버 wipe.

### v2 — 확장
- 실행 기록 동기화, 삭제 전파(tombstone), (원하면) 지속 백그라운드 동기화, 다기기 동시성.
