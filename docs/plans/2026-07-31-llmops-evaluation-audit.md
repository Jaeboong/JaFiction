# 2026-07-31 — LLMOps 평가 체계 감사 및 설계 (논의용)

**Status:** draft — 논의용. 확정 전이며 착수 승인 없음.
**Scope:** (1) 외부 비평문의 주장을 코드 실측으로 검증/정정, (2) 이 프로젝트에 없는 것이 정확히 무엇인지 확정, (3) 평가 체계(루브릭·골든셋·judge·핵심가설 A/B) 설계안 제시.
**Driving data:** 본 문서 §2 실측표. 모든 판정은 파일:라인 근거를 가진다.

## 0. 이 문서를 쓰는 이유

"프로젝트에 허점이 많다"는 외부 비평이 있었다. 그 비평을 검증 없이 받아 안고 대응을 설계하면,
**검증되지 않은 전제 위에 작업을 쌓는다**는 비평 자체의 지적을 그대로 반복하게 된다.
따라서 대응의 첫 단계는 비평문의 주장을 코드로 falsify 하는 것이다.

## 1. 검증 방법

- 조사는 3개 독립 서브에이전트에 분할 위임 (지정 질문 기반, 파일:라인 인용 강제, 파일 수정 금지)
- 각 주장은 **확정 / 정정 / 확정불가** 3분류
- 근거가 문서(plan)뿐인 주장은 "문서상 주장"으로 별도 표기하고 코드로 재확인

### 2.1 #1 정정의 실제 함의 — 더 나쁜 쪽으로

테스트는 있다. 그런데 51개 전부가 **가짜 provider에 스크립트된 응답을 물려놓고 상태 전이·파싱·프롬프트 조립만 검증**한다.
resume, abort 전파, 개입 주입, BLOCK 에스컬레이션, 리뷰어 부분 실패, 한국어 강제, 스트리밍 새니타이즈, 티켓 파싱 — 전부 기계 동작이다.

**생성된 초안의 품질을 assert 하는 테스트는 0개다.**

정확한 진술은 "테스트가 없다"가 아니라 **"있는 테스트 전부가 출력 품질과 직교하는 축을 잰다"** 이다.
비평문의 결론(노력이 검증 가능한 쪽으로 흘렀다)은 유지되고, 근거만 교체된다.

### 2.2 #2 정정 — 그리고 실제 문제는 다른 곳

`scripts/fetch-posting-fixtures.ts:743-761` 실측 계산식:

```
분모 = (classification === "success" 인 fixture 수) × 5필드
분자 = 그 중 fieldSources[field] === "factual" 인 개수
→ 43.8% = 46 / 105  (= 21건 × 5필드)
```

fixture 총괄 (`completed_plans/2026-04-17-posting-parser-fixtures/report.md`):

| 분류 | 건수 | 비율 |
|---|---|---|
| success | 21 | **28.0%** |
| partial | 50 | 66.7% |
| total_failure / expired / error | 4 | 5.3% |
| 합계 | 75 | 100% |

**게이트 지표가 성공 부분집합(28%)에 조건부로 걸려 있다.** 나머지 72%는 분모에 들어오지 않는다.
전체 모집단 기준 환산 시 `46 / (75×5) = 12.3%`.

이는 survivorship-conditioned metric이며, "40% 게이트 통과"가 무엇을 보증하는지 정의상 모호해진다.
비평문이 말한 방향("절반이 막힌다")보다 실제로 더 나쁘지만, 그 근거는 달랐다.

추가로 success 21건 **내부**에서도:

| 필드 | factual 비율 |
|---|---|
| companyName | 100% |
| roleName | 76% |
| mainResponsibilities | 43% |
| qualifications | **0%** |
| preferredQualifications | **0%** |

자소서 작성에 가장 직접적으로 필요한 두 필드가 최선의 부분집합에서조차 전부 비-factual이다.

도메인 그룹별 성공률: `recruiter_co_kr` 9건 **0%**, `kia` 6건 **0%**, `posco` 3건 **0%**, `careerlink` 3건 **0%**, `jumpit` 17건 12% /
`jobkorea` 100%, `greetinghr` 100%, `wanted` 82%.
**0%인 그룹이 정확히 P2 plan의 어댑터 대상 목록**(`p2-major-adapters.md:205-213`)이다.
즉 "어댑터 0개"는 추상화 취향 문제가 아니라 실측 실패의 대부분을 방치했다는 뜻이다.

### 2.3 생성물 품질 평가 장치 — 전수조사 결과

| 범주 | 존재 | 재는 대상 |
|---|---|---|
| DART 섹션 트리 골든 (`services/filings-retrieval/eval/goldens/`) | 있음 | 파서 출력 (결정론적) |
| 공고 추출 골든 (`packages/shared/src/test/goldens/posting/`) | 있음 | 파서 출력 (결정론적) |

| 런타임 수렴 판정 (`convergenceEvaluator.ts`, `discussionLedger.ts`) | 있음 | LLM 생성물 품질 — 단 3분류 라벨(PASS/REVISE/BLOCK), 숫자 없음, 골든셋 없음, run 간 비교 미보존 |

런타임 자기수렴 메커니즘(리뷰어 판정)은 존재하지만, 이는 생성 루프 내부의 진행 제어이지 평가 하니스가 아니다.

## 3. 비평문에 없던 발견

### 3.1 판단기준은 존재한다 — 다만 조작화되지 않았다

`packages/shared/src/core/storage.ts:759` `defaultRubric()`:

```
- question fit
- specificity/evidence
- impact/metrics
- role/company fit
- clarity/structure
- tone/authenticity
```

이것이 `contextCompiler.ts:92-93`에서 `## Evaluation Rubric` 섹션으로 컴파일되어 리뷰어 프롬프트에 실린다
(`realtimePrompts.ts:232-317`). 프로젝트별 편집 가능 필드다.

**즉 "판단기준이 없다"는 틀렸다. 6개 차원이 이미 정의되어 있고, 리뷰어 3인의 관점
(`participants.ts:62-94` — technical / interviewer / authenticity)과도 대략 대응한다.**

없는 것은 기준이 아니라 **조작적 정의**다: 척도 없음, 앵커(각 점수의 의미) 없음, 차원별 판정 미분리,
점수 미산출, 미보존, run 간 비교 불가. 6개의 맨 불릿 문자열이 프롬프트에 그대로 들어갈 뿐이다.

→ 이건 나쁜 소식이 아니라 좋은 소식이다. 평가 체계를 0에서 발명할 필요가 없고,
**이미 프롬프트에 실려 있는 6차원을 앵커드 루브릭으로 승격**시키는 것이 출발점이 된다.

### 3.2 프로덕션 경로에 라운드 상한이 없다 — 회귀다, 원래 작동했다

**이건 미구현이 아니라 지워진 기능이다.**

```
9eecf55 (2026-04-10)  orchestrator.ts:1445
  const reachedSectionRoundLimit = currentSectionRoundCount >= maxRoundsPerSection;   ← 작동

924415b (2026-04-10)  "feat(runs): redesign agent conversation and draft workflow"
  → 이 줄 소실. 이후 현재까지 부재
```

**3개월 반 동안 검출되지 않은 이유 — 이름이 거짓말하는 테스트:**

`orchestrator.test.ts:3539` `test("realtime mode pauses at the configured section round limit when blocking issues remain")`
는 이름과 달리 라운드 상한을 검증하지 않는다. `maxRoundsPerSection: 3`을 넣지만 라운드는 1번만 돌고
(BLOCK 에스컬레이션 경로), assert는 전부 blocking·awaiting-user-input에 관한 것이다. **상한에 닿지도 않는다.**

→ §2.1("51개 테스트가 출력 품질과 직교하는 축을 잰다")의 가장 구체적인 실례다.
테스트 이름이 커버리지를 주장하지만 assert가 그것을 확인하지 않으면, 실제 기능이 죽어도 초록불이 유지된다.

- `maxRoundsPerSection`은 1~10으로 클램프되어 run 레코드에 **저장만** 되고,
  루프 종료 조건으로 읽히는 곳이 코드베이스에 없다 (`convergenceEvaluator.ts:184-190`, 전체 grep 확인).
- 유일한 자동 상한 `autoCycleLimit`(`orchestrator.ts:415, 828`)은 `interactiveMode === false`일 때만 유효한데,
  프로덕션 유일 호출부(`runsHandlers.ts:412-438`)가 항상 `requestUserIntervention`을 전달하므로
  `interactiveMode`는 항상 true → **이 분기는 프로덕션에서 도달 불가능**하다.
- 실사용에서 cycle/round 수는 사용자가 `/done`·`/stop`·`/abort`를 입력할 때까지 무제한.

**함의:** cycle당 7콜 × 무제한 라운드. 비용 상한이 코드가 아니라 사용자의 인내심으로 결정된다.
평가 이전에 이것부터가 운영 리스크다.

### 3.3 리뷰어 3인은 하드코딩이다

`participants.ts:62-94`는 항상 정확히 3명(evidence / fit / voice)을 반환한다.
`reviewerProviders` 설정은 "몇 명"이 아니라 "이 고정 3역할에 어떤 provider를 배정할지"만 정한다.
→ "리뷰어 수"는 실험 변수로 노출되어 있지 않다. A/B에서 3인 vs 1인을 비교하려면 이 함수부터 파라미터화해야 한다.

### 3.4 리뷰어 탈락은 영구적이다

`orchestrator.ts:744-748` — 리뷰어 1명이 실패하면 `activeReviewers.splice()`로 배열에서 제거되고
**run이 끝날 때까지 복귀하지 않는다**. 즉 첫 cycle에서 voice reviewer가 죽으면 이후 모든 cycle이
2인 리뷰로 진행되며, 사용자는 그 사실을 명시적으로 통보받지 않는다.
"관점 분리가 품질을 만든다"는 프로젝트의 핵심 가설을, 런타임이 조용히 훼손할 수 있는 경로다.

### 3.5 Notion 프리패스는 자동 발동한다

`notionRequest.ts:20-41` — 사용자가 아무 요청을 하지 않아도 프로젝트에 `notionPageIds`가 하나라도
등록돼 있으면 `kind: "auto"`로 프리패스 1콜이 발생한다. run당 최대 1회이므로 cycle 계산에는 영향 없으나,
비용 계산 시 누락되기 쉬운 항목이다.

### 3.6 두 모드의 리뷰어 협업 의미론이 다르다 (핵심 가설의 정의에 직접 영향)

**deepFeedback — 리뷰어들은 서로를 보지 못한다.**

- `orchestrator.ts:634` — 리뷰어 루프 **진입 전에** `completedReviewerTurns` 스냅샷을 뜬다
- `orchestrator.ts:718` — 루프 안의 `buildDeepReviewerPrompt(..., completedReviewerTurns, ...)`가 그 스냅샷을 쓴다
- `orchestrator.ts:707, 742` — 이번 cycle의 리뷰어 출력은 `currentCycleReviewerTurns`에 쌓이지만,
  이건 `:759`(coordinator decision)와 `:790`(finalizer)에만 전달된다

→ 같은 cycle 안의 리뷰어 3인은 **서로의 지적을 보지 못한다.** 순차 실행이지만 데이터 의존은 없다.

**그러나 "독립 심사자 앙상블"은 절반만 맞다 — 교차는 있고, 한 사이클 지연되어 있다.**

- `deepFeedbackPrompts.ts:194-199` — 프롬프트 빌더에 **같은 라운드의 다른 리뷰어를 명시적으로 가리는 필터**가 있다.
  호출부가 이미 이전 사이클 스냅샷만 넘기므로 현재 dead code지만, 바로 그래서 **의도의 선언문**이다.
  사이클 내 blind는 사고가 아니라 설계다
- `deepFeedbackPrompts.ts:201-205` — `previousBlock`이 **이전 사이클** 리뷰어 노트를 `.slice(-4)`로 주입한다

→ 정확한 성격은 **"사이클 내 독립 심사 / 사이클 간 지연 교차 심의(delayed cross-deliberation)"**다.

**실험에 직결되는 함정:** 교차 채널이 사이클 간에만 있으므로, **arm E를 1 사이클로 측정하면 설계의 핵심 기제가
한 번도 발화하지 않은 채로 재게 된다.** 그 상태의 "파이프라인이 값어치를 못 한다"는 발견이 아니라 하네스 아티팩트다.
`schemas.ts:261`의 `rounds: z.number().int().min(0)`은 **0을 통과시키고**,
`orchestrator.ts:415` `Math.max(1, request.rounds || 1)`이 이를 **조용히 1로 바꾼다**(에러·경고 없음).
→ 사이클 수를 실험 변수로 명시·고정·보고하고, **arm E는 ≥2 사이클**이어야 한다.

### 3.6.1 실제 결함 — 사이클 1의 계약 위반

`deepFeedbackPrompts.ts:230`은 `## Direct Responses To Other Reviewers`를 **필수 출력 섹션**으로 요구하고,
`:220`은 "You are a role-specific reviewer collaborating with other model reviewers"라고 선언한다.
그런데 사이클 1의 해당 입력은 `_No prior reviewer notes yet._`다.

→ **모든 run의 사이클 1에서, 리뷰어는 본 적 없는 동료에게 "직접 응답"하라는 요구를 받는다.** 환각 유도 조건이다.

`orchestrator.test.ts`의 FakeGateway 응답은 이 자리에 `- None` 등을 하드코딩해 두었으므로
**현행 테스트는 이 결함을 원리적으로 잡을 수 없다**(배선만 보므로).

수정안: 사이클 1에 한해 이 섹션을 optional로. **judge 없이 결정론적으로 잴 수 있는 지표**이기도 하다 —
"사이클 1 출력에서 존재하지 않는 동료를 지칭한 비율". 하네스 초기 지표로 싸고 강하다.

**realtime — 리뷰어들은 서로를 본다.**

- `orchestrator.ts:1319` — `turns.filter((turn) => turn.status === "completed")`가 **루프 안에서** 평가되고,
  각 리뷰어 종료 시 `turns.push(turn)`이 실행된다 → reviewer 2의 프롬프트에 reviewer 1의 이번 라운드 출력이 들어간다

→ 같은 라운드의 리뷰어들이 **순차 토의**를 한다. (`orchestrator.test.ts`의 cross-feedback 참조 테스트들이 이 경로다.)

**함의 — 이게 왜 중요한가:**

1. 프로젝트의 가설("관점을 분리해 검토하면 낫다")이 **두 모드에서 서로 다른 것을 의미한다.**
   deepFeedback은 *독립 심사자 앙상블*, realtime은 *순차 토의*다. 하나의 A/B로 둘을 동시에 검증할 수 없다.
2. deepFeedback 리뷰어 순차 실행은 **구현 아티팩트지 아키텍처가 아니다.** 이 상태로 wall-clock을 재면
   파이프라인이 부당하게 불리해진다 → §5.5 latency 보고 규칙 참조.
3. 병렬화가 "공짜"는 아니다. 처리해야 할 것: (a) `stateMap.get(reviewer.providerId)` — 두 리뷰어가 같은
   providerId면 state 공유 레이스, (b) `eventSink`/`turns` push 순서 비결정화(스냅샷 테스트 파손),
   (c) 실패 시 `activeReviewers.splice()`가 순서 의존적.

### 3.7 Python 게이트는 CI에 없다

`scripts/check.sh` → `test-all.sh`(vitest) + web build + `docs-check.sh`.
`services/filings-retrieval`의 pytest 54개는 여기에도, `.github/workflows/test.yml`에도 포함되지 않는다.
DART P0의 "게이트 PASS 20/20"은 **수동 실행으로만 재현되며 PR 게이트가 지키지 않는다.**
(P2 plan에 `scripts/check-filings.sh` 신설이 예정되어 있으나 미착수.)

## 4. 진단 — 무엇이 진짜 공백인가

비평문의 프레임("검증 가능한 것만 쟀다")은 맞지만, 한 단계 더 들어가면 원인은 이렇다.

이 프로젝트가 측정한 것들은 전부 **정답이 외부에 존재하는** 문제다 (공고 HTML의 회사명, 공시 XML의 섹션 트리).
측정하지 못한 것은 **정답을 스스로 정의해야 하는** 문제다 (좋은 자소서란 무엇인가).

그리고 후자의 정의는 **이미 6개 차원으로 존재한다**(§3.1). 다만 그것을 프롬프트에 넣는 데서 멈췄고,
**측정 도구로 승격시키지 않았다.** 정확히 말하면 런타임에 리뷰어 LLM이 이 루브릭으로 초안을 판정하기는 하지만,
그 판정이 3분류 라벨로 소비되고 사라지므로 **오프라인·재현가능·비교가능한 측정은 0건**이다. 그래서:

- 7콜이 1콜보다 나은지 물을 수 없고
- 리뷰어 3인이 1인보다 나은지 물을 수 없고
- DART 근거 주입이 도움이 되는지 물을 수 없고 (P3 게이트가 이걸 하려던 것)
- 프롬프트를 바꿨을 때 나아졌는지 나빠졌는지 알 수 없다

**즉 공백은 "평가 인프라 부재"가 아니라 "이미 있는 판단기준의 미조작화"다.**
이 구분이 중요한 이유: 전자로 접근하면 eval 프레임워크를 새로 짓게 되고,
그것은 "인프라 먼저, 구현체 0개"의 네 번째 사례가 된다.

## 5. 설계안

### 5.1 순서 원칙

```
루브릭 조작화 → 골든셋(소규모) → judge 캘리브레이션 → 핵심가설 A/B → 그다음에 기능
```

각 단계는 **다음 단계가 그것 없이는 불가능**하기 때문에 이 순서다. 인프라를 먼저 짓는 순서가 아니다.

### 5.2 Step 1 — 루브릭 조작화 (기존 `defaultRubric()` 승격)

6개 차원 유지, 각 차원에 **1–5 척도 + 앵커 정의**를 붙인다. 예시(evidence 차원):

```
specificity/evidence
  5 — 모든 주장이 지원자의 구체적 경험(시기·역할·수치)으로 뒷받침됨
  3 — 주장의 절반가량이 구체적 근거를 가짐. 나머지는 일반론
  1 — 검증 가능한 구체 사실이 사실상 없음
```

- 저장 위치: `defaultRubric()`을 척도 포함 형태로 확장 (프로젝트별 편집 가능성 유지)
- **부수 효과 주의**: 이 문자열은 리뷰어 프롬프트에 그대로 실린다 → 루브릭 변경은 런타임 동작 변경이다.
  따라서 조작화 버전을 프롬프트용과 평가용으로 분리할지 결정 필요 (§6 Q1)

### 5.3 Step 2 — 골든셋

**"모범 답안 골든셋"은 만들지 않는다 (2026-07-31 설계 변경).**

당초 안은 본인이 쓴 자소서에 6차원 절대 점수를 매겨 정답으로 삼는 것이었다. 사용자 지적으로 폐기한다:
**본인도 자기 자소서가 정답이라고 장담할 수 없다.** 웹에서 수집한 합격 사례도 대안이 못 된다 —
남의 경험으로 쓴 글이라 우리 시스템이 낼 수 있는 출력의 기준이 되지 않는다.

**절대 기준 대신 상대 비교로 간다. 이러면 정답이 필요 없다.**

A/B가 실제로 묻는 것은 "이 자소서가 몇 점인가"가 아니라 **"둘 중 어느 쪽이 나은가"**뿐이다.
전자는 ground truth가 필요하지만 후자는 필요 없다. 따라서 필요한 것은:

| 자산 | 규모 | 정답 라벨 |
|---|---|---|
| (실제 공고, 실제 문항) 쌍 | 15~20 | **불필요** |
| 사람이 판정한 pairwise 비교 | 20~30쌍 | 필요 — 단 "어느 쪽이 나은가"만 |

- 출처: `~/project/apply`의 실제 지원 이력 (공고·문항만 쓰고 초안은 실험이 생성)
- 사람 판정이 필요한 유일한 이유: **judge가 본인 감각과 맞는지 확인**. 안 맞으면 A/B 전체가 노이즈다
- 난이도 분산: 명백한 우열 / 미세한 차이를 섞는다. 전부 미세하면 일치도를 측정할 수 없다
- 6차원 점수는 여전히 산출한다 — 단 **결론의 근거가 아니라 진단용**이다
  ("E가 이겼다"가 결론, "evidence에서 이기고 tone에서 졌다"가 진단)
- 개인정보: 공고·문항에는 개인정보가 없다. 원래 우려했던 실명·연락처 문제가 대부분 사라진다

### 5.4 Step 3 — LLM-as-judge 캘리브레이션

**judge를 먼저 신뢰하지 않는다. 사람 점수와의 일치도를 먼저 잰다.**

**자소서는 ground truth가 없다. 따라서 모든 결론은 사실상 judge에 대한 주장이 된다.** 최소 요건:

- 산출: 6차원 각각 1–5 점수 + 근거 문장 (총점 단일 판정 금지 — "어느 쪽이 나은가"가 아니라 루브릭 고정)
- 검증 지표: 사람 점수와의 **Spearman 상관** 및 **±1 이내 일치율**
- 채택 기준(제안): 차원별 ±1 일치율 ≥ 0.80. 미달 차원은 앵커를 고쳐 재측정
- **위치 편향**: pairwise 비교는 **양방향 실행(위치 스왑)** 필수. LLM judge의 position bias는 크다
- **self-preference**: judge provider가 참가 provider와 겹치면 오염. **judge 2종 이상**으로 결론 안정성 확인
- **반복성 먼저**: 같은 입력을 여러 번 채점했을 때의 점수 SD를 먼저 잰다. 흔들림 크기를 모르면
  arm 간 점수차가 신호인지 노이즈인지 판정할 수 없다 (→ §5.4.1 선행 자산)
- **judge-human 일치도가 우연 수준이면 A/B 전체가 노이즈다. 이걸 진행 게이트로 건다.**

#### 5.4.1 선행 자산 — `~/project/apply/research_company/experiments/`

별도 repo(`apply`)에 **점수 반복성 실험 하니스**가 이미 존재한다:
`sample.mjs`(표본 추출) → `judge.mjs`(프롬프트 생성, `--emit`/`--call`) → `analyze.mjs`(SD 분석), `README.md`.
묻는 질문이 "같은 대상을 여러 번 판정하면 점수가 얼마나 흔들리는가"로, **본 설계의 반복성 선행 측정과 정확히 같은 문제**다.
바퀴를 재발명하기 전에 이 하니스의 구조(프롬프트 emit → 수동/자동 호출 → 회차별 JSON → SD 집계)를 먼저 검토한다.
단, 대상이 다르다(공고 판정 vs 자소서 초안 채점) — 재사용은 **구조**이지 프롬프트가 아니다.

### 5.5 Step 4 — 핵심 가설 A/B

**arm 설계 — "7콜 vs 1콜" 이진 비교는 버린다.**

두 arm은 한 변수만 다르지 않다. 지배적 교란은 토큰 예산이 아니라 **7콜이 서로 다른 provider에 걸쳐 있다는 점**이고,
단일콜 베이스라인은 이걸 원리적으로 재현할 수 없다. 이기든 지든 행동 가능한 결론이 안 나온다.
대신 판별력 있는 지점만 집는 ablation 사다리로 간다:

| arm | 구성 | 콜 수 | 프로덕션 변경 |
|---|---|---|---|
| A (단일샷) | 동일 컨텍스트 + 문항 → 1콜 | 1 | 신규 빌더 필요 |
| C (자기비평) | 단일 모델 draft → self-critique → revise | 3 | 신규 빌더 필요 |
| D (다양성) | draft → 서로 다른 모델 N개 review → revise | 2+N | 리뷰어 수 파라미터화 필요 |
| E (현행) | deepFeedback, **≥2 cycle** (§3.6 — 1 cycle이면 교차 심의 미발화) | (4+N)×cycles | 없음 |

**arm A/C의 경계 = "완성된 산출물을 관찰하는 별도 패스가 있는가" (= 콜 수).** 취향이 아니라 기계적 판정선이다.
- A = 1콜. **루브릭을 프롬프트에 넣는 것도, 응답 내부 자기점검/CoT도 허용**한다.
  루브릭은 생성 중 따르는 지시일 뿐 관찰 패스가 아니므로 A가 C로 변질되지 않는다
- C = 2콜 이상. 콜 2가 **콜 1의 완성된 출력을 입력으로 본다**
→ 이렇게 그으면 A→C 델타가 정확히 **"별도 관찰 패스가 값어치를 하는가"**를 측정한다.

**"역할 지시를 제거한 A"는 만들지 않는다 — 스트로맨이다.** 의사결정 질문이 "파이프라인을 출시할까 단일콜을
출시할까"이므로, 베이스라인은 **유능한 엔지니어가 실제로 출시할 최강의 1콜 구성**이어야 한다.
구조를 삭제한 A를 이기는 건 정보가 없다. 삭제형 ablation은 C·D가 할 일이다.

**arm A 공정성 통제 4개:**
1. **동일 컨텍스트** — `buildCompiledContextMarkdown(..., "full")` + 동일 Notion brief 프로파일.
   따로 만들면 오케스트레이션이 아니라 리트리벌을 재게 된다
2. **동일 출력 계약** — E의 최종물은 finalizer(`finalDraft`/`finalChecks`) + coordinator decision(`summary`/`improvementPlan`)이다.
   A도 같은 필드를 내야 한다. 아니면 출력 형태 자체가 교란이 되고 judge가 형태를 보고 찍는다
3. **A의 모델도 변수다** — E에 쓰인 provider **각각으로 A를 돌려 best-of를 보고**한다. 스트로맨 회피의 핵심
4. **토큰은 균등화하지 않고 보고한다** — 균등화하면 A에 패딩을 강요하게 된다. 비용은 품질/1k토큰 축으로

**A 프롬프트는 judge 점수를 보기 전에 동결한다.** A를 보면서 고치는 순간 실험이 죽는다.

**읽는 법이 명확하다는 게 이 설계의 이유다:**

- `C ≈ E` → coordinator·finalizer·멀티프로바이더 기계장치는 장식이다 (삭제 근거)
- `D ≫ C` → **프로바이더 다양성이 load-bearing**이다. 그러면 어떤 단일콜 베이스라인도 원리적으로 따라올 수 없고,
  질문이 "파이프라인이 값어치를 하는가"에서 **"어느 단계가 값어치를 하는가"**로 바뀐다. 후자가 훨씬 쓸모 있다
- `A ≈ E` → 가장 강한 결론이지만, §5.7의 측정 밖 축을 반드시 함께 보고해야 한다

**대상 모드는 deepFeedback으로 한정한다.** 두 가지 근거가 겹친다:
(a) §3.6 — realtime은 리뷰어가 서로를 보는 다른 구조라 같은 실험에 섞으면 무엇을 쟀는지 알 수 없다.
(b) **배포된 웹에서 realtime 모드는 실제로 사용되지 않는다** (사용자 확인, 2026-07-31).
따라서 realtime의 §3.6 비대칭은 실험 설계상 고려 대상에서 제외한다 — 다만 코드에는 남아 있으므로
두 모드가 다른 협업 의미론을 구현한다는 사실 자체는 유지 보수 관점에서 유효하다.

**latency 보고 규칙:** deepFeedback 리뷰어 순차 실행은 구현 아티팩트다(§3.6). wall-clock은
**"순차 실측 / 병렬 가정치"를 병기**한다. 순차값만 보고하면 아키텍처가 아니라 구현을 벌주게 된다.

- **하니스 재사용은 평가 절반에만 해당한다 (비용 과소평가 주의).**
  `2026-07-04-dart-filings-rag.md:221`의 설계에서 **채점·paired 비교·통계 판정 부분은 그대로 쓸 수 있다.**
  그러나 P3의 두 arm은 *같은 drafter 빌더에 블록만 넣고 뺐던* 반면, 여기의 arm들은 **파이프라인 위상 자체가 다르다.**
  따라서 생성 쪽에는 신규 작업이 필요하다:
  - **arm A**: 단일샷용 프롬프트 빌더가 존재하지 않는다. 기존 빌더는 전부 역할 구조(coordinator brief·ledger·reviewer 참조)를 전제한다 → 신규 작성
  - **arm C**: `buildReviewerParticipants`가 3인 고정이다(§3.3) → 리뷰어 수를 파라미터화하는 **프로덕션 코드 변경** 필요
  - arm B만 현행 코드로 그대로 실행 가능
  arm C를 빼고 A vs B만 먼저 돌리면 프로덕션 변경 없이 시작할 수 있다. 이쪽을 권장한다.
- paired 설계: 동일 (공고, 문항)에 모든 arm을 돌린다. 반복 3회로 LLM 비결정성 흡수
- **규모**: n=10짜리 승률은 CI가 ±30%p라 무의미하다. **문항 15~20 × 양방향 판정 → 60~80 paired 판정**이 하한
- **arm 수는 검정력을 깎지 않는다** (초안의 오류를 정정). within-item paired 설계에서 같은 문항 집합에 A·C·E를
  모두 생성하면 각 문항이 A-vs-C, C-vs-E, A-vs-E 판정을 **각각** 낳는다. 즉 **대비(contrast)당 n = 문항 수**이고
  arm을 늘려도 줄지 않는다. 늘어나는 건 생성·판정 **예산**이지 검정력이 아니다
- **1차는 A vs C vs E 3-arm**으로 간다. A vs E만 돌리면 §5.5에서 폐기하기로 한 교란(콜 수·모델 수·관찰 패스·사이클 수가
  동시에 다름)이 그대로 재현되어 어느 쪽이 나와도 행동 불가다. C가 정보량이 가장 큰 arm이다
- 예산이 부족하면 **arm이 아니라 문항당 seed 수를 줄인다.** judge 2종·위치 스왑은 어떤 경우에도 깎지 않는다
- 판정: 6차원 합산 점수의 Wilcoxon signed-rank + 차원별 개별 보고
  (총점만 보면 "evidence는 올랐는데 tone은 떨어졌다"를 놓친다)
- **판정 규칙 사전 등록**: 예 — "해당 단계 제거 시 점수 하락의 95% CI가 0을 포함하면 그 단계는 삭제 대상".
  사후에 기준을 정하면 p-hacking이다
- **비용 축 병행 보고 필수**: 품질 개선 폭을 7배 비용으로 나눈 값이 실제 의사결정 근거다.
  B가 A보다 유의하게 낫더라도 개선폭이 작으면 결론은 "C로 축소"일 수 있다

### 5.6 측정하지 않는 축 — 먼저 선언한다

파이프라인의 정당화 근거 중 **품질이 아닌 것들**이 있고, 어떤 A/B도 이걸 못 잰다.
결과 해석 시 이걸 빠뜨리면 정직하지 않은 결론이 나오므로 미리 박아둔다:

- **사이클 사이 사용자 개입** — `requestUserIntervention`, `/done`·`/abort`, userInterventions 재주입.
  단일콜에는 개입 지점 자체가 없다. 이건 품질이 아니라 제품 기능이다
- **토의 과정의 가시성** — eventSink → 웹 UI 렌더. 사용자가 보는 게 곧 제품이다
- **실패 격리** — 리뷰어 1명이 죽어도 나머지로 진행된다(§3.4). 단일콜은 부분 열화라는 개념이 없다

→ **"단일콜이 품질 동등"이 나와도 정직한 결론은 "품질 동등, 단 위 3가지를 잃는다"이지 "파이프라인 삭제"가 아니다.**

### 5.7 예상 결과에 대한 사전 선언 (중요)

**A/B를 돌리기 전에 예측을 기록한다.** 결과를 보고 나서 해석을 만들면 측정의 의미가 없다.
사전 예측과 실제 결과의 불일치 자체가 가장 정보량이 큰 산출물이다.

또한 **"B가 진다"는 결과를 받아들일 준비를 하고 시작한다.** 그 경우의 행동은
"파이프라인을 버린다"가 아니라 "어느 차원에서 지는지 보고 그 단계를 제거한다"이다.
질 수 있는 실험만이 정보를 준다.

## 7. 착수 조건 — 무엇이 목적에 무관한가

Step 1~3(루브릭 조작화 · 골든셋 20~30건 · judge 캘리브레이션)은 **§6 Q3(제품 개선이냐 포트폴리오냐)에
무관하게 동일하다.** 어느 목적이든 앵커드 루브릭과 사람 기준점 없이는 아무것도 잴 수 없기 때문이다.
따라서 Q3는 착수를 막는 질문이 아니며, **Step 4에서만 갈린다**:

- 제품 개선이 목적: "나에게 B가 A보다 나은가"에서 멈춘다. n을 작게, 판정은 본인 감각 우선
- 포트폴리오가 목적: 통계 리포트·재현 패키징·judge 신뢰도 문서화까지 간다. n을 키우고 CI에 물린다

실제로 막는 것은 **Q1(루브릭 이원화)뿐이다** — 이건 Step 1의 산출물 형태를 직접 결정하므로 먼저 답이 필요하다.
Q2(골든셋 커밋 여부)는 Step 2 직전까지, Q4(예산)는 Step 4 직전까지 미룰 수 있다.
Q5(라운드 상한 부재)는 평가 작업과 독립적이며 지금 고칠 수 있다.
